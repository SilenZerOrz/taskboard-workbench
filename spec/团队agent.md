# 团队 agent.md · Agent Team 任务工作台

> **用途**：约束本项目「Agent Team 任务工作台」下的**多智能体团队**如何创建、派发、执行与回写。
> **适用范围**：所有经工作台/承载环境（DSH）创建的团队与其成员；也作为本仓库后续"自举开发"的团队契约。
> **上位依据**：[`需求文档.md`](./需求文档.md)（§二 K/L，FR-34…FR-48）、[`规范/04-决策与复盘.md`](./规范/04-决策与复盘.md)（外部 CLI 执行器）。
> **状态**：v1.1（2026-10-14 首版；2026-10-23 增补 §8.1 分域声明 —— **只增不改，角色定义未动**）。技术实现随后续切片推进；本文先锁**契约与红线**。
> **测试/开发环境指定的引擎插件**：**`@nanmicoder/dsh-agent-teams`（v0.1.22）**——队长派发/成员执行经该插件（T-5 兼容性见 [`计划文档.md`](./计划文档.md)）。

## 一、角色（成员集合）

| 角色 | id | 职责 | 写权限 |
| --- | --- | --- | --- |
| 队长 | `lead` | 领取目标任务 → 按模板派发 → 汇总回流 → 不解锁下游直到审查通过 | 派发、汇总；**不得置 done** |
| 规划 | `planner` | 需求拆解、可行性、技术任务与依赖 | 产出需求/任务；不改实现代码 |
| 开发 | `engineer` | 实现代码（可调外部 code CLI） | 指定文件；**不得 commit/push**（commit 归队长/人） |
| 测试 | `tester` | 验证、回归、缺陷复现 | 测试与报告；**不得写实现代码** |
| 评审 | `reviewer` | 质量门审查；审查未过不得解锁下游 | 审查结论 |
| 归档 | `archivist` | 文档、索引、交付 | 文档区 |

> 最小团队 = `lead` + `engineer` + `tester`；含质量门时加 `reviewer`。

## 二、团队创建要求（模板字段）

创建团队前**须给定模板**（缺一不可）：

1. **roles**：角色集合与数量（默认 `lead×1, engineer≥1, tester≥1[, reviewer]`）。
2. **per-role model**：每个角色的模型（可留空=默认）。
3. **per-role executor**：每角色的执行器——`hosted`（承载环境内智能体）/ `cli:codex` / `cli:claude` / 其他外部 code CLI。
4. **quality gates**：质量门顺序（默认 `需求→实现→验证→审查→集成`）。
5. **target**：目标任务或需求条目（**必须已归因**；否则拒建）。

**硬性校验**：目标未归因 → 拒绝；角色缺失或数量为 0 → 拒绝；同一任务已有活跃执行单元 → 拒绝（任务级锁）。

### 附：项目环境与约束（随团队一起约定）

创建团队时**同时约定项目环境与约束**（存于项目设置，见 FR-56）：工作区路径、语言/时区、构建与测试命令、编码约定、红线（不得 commit/push、不得写 done 等）。团队执行时**以该约束为项目上下文**。

## 二·序、团队先于任务（项目入口）

> 顺序权威：`需求文档.md` §三 场景六「项目从零到执行（团队先行）」；需求 §二 N（FR-55…FR-59）。

- 工作台页 = 项目团队的**项目入口**；**项目文档可以尚未完善**时即进入。
- **入口是"会话优先"**：先在一个会话里打开工作台（该会话即项目的**初始会话**，FR-60），再在该会话内做项目配置；开局用[`规范/项目开局提示词`](./规范/02-流程与开局规范.md)提醒"创建会话时加载工作台插件 + 指定 agent team 插件"（FR-61）。
- **两种入口**（FR-62/63）：① 从 DSH 列表的「任务工作台」按钮进入 = **全局入口**，默认进"近期执行"项目，可用顶部下拉切换；② 从**会话区**进入 = **会话入口**，默认加载该会话已绑定的项目；**未绑定会话不显示工作台数据**，可经对话申请关联、由**项目主会话批准**后生效。
- **团队的第一使命不是执行，而是"把空项目变成需求与任务"**：
  1. 引入项目资料（md/doc）；
  2. **需求梳理 → 优化 → 落盘需求文档**（FR-58）；
  3. 定稿后**拆解成看板任务**并归因（FR-59）。
- **只有走到"已归因任务"之后，才进入执行**（队长派发 → 成员执行 → 反馈，FR-49/51）。
- 因此：**未归因任务被归因门拦截是预期**，不是"缺 todo"。

## 三、派发协议（入口 = 队长）

- **入口固定为承载环境（DSH）创建的 agent team 队长**：由队长领取目标任务并向下派发；不由人逐条手点。
- 派发顺序：按依赖就绪逐个认领；上游未就绪的任务**不得开工**。
- 队长可**反向调用**成员：为成员生成子任务（`team_tasks`）并指向成员角色/执行器。
- 目标未归因 / 任务在 `backlog` → **拦截**（未授权不开工）。

### 反向调用链（示意）

```
人/工作台 ──派发──▶ 队长(lead)
                     │  按模板 + 依赖
                     ▼
             成员(engineer/tester/reviewer/archivist)
                     │  执行（hosted 或 cli:codex/cli:claude）
                     ▼
             反馈回写 ──▶ 工作台(任务/团队状态 + 审计)
```

## 四、执行器规范（可配置外部 code CLI）

- **执行器可配置**：代码执行成员（`engineer`，必要时 `tester` 的复现脚本）可配置为外部 code CLI，如 `codex`、`claude`。
- **必须非交互**：显式非交互模式（如 `claude -p` / `codex exec`），**不得进入交互式会话**（会挂住）。
- **显式授权目录**：必须使用绝对路径；跨目录需显式授权（如 `--add-dir`）。
- **配额回退**：调用前做极短探测；配额不足 → **回退为成员自行执行**，并注明"因配额回退"，**不降低验收标准**。
- **不采信未复核输出**：外部 CLI 的产出必须经成员复核 + 自测（`node --check` + `node --test`）。
- 细节与边界见 [`规范/04-决策与复盘.md`](./规范/04-决策与复盘.md)。

## 五、反馈回写契约（成员 → 工作台）

成员每次执行**必须回写**以下最小集：

| 字段 | 含义 |
| --- | --- |
| `teamTask.status` | `open` / `running` / `completed` / `failed` / `cancelled` |
| `attempt.result` | 本次尝试结果（`passed` / `failed` / `blocked` + 简述） |
| `evidence` | 产出证据：diff 摘要 / 退出码 / 测试结果 / 复现步骤 |
| `actor` | 成员标识（角色 + 实例） |

- 回写经**工作台 API**（不是直接改库）：`/api/teams/:id/tasks/:tt/outcome`、`/api/teams/:id/progress`、`/api/tasks/:ref/team-status`。
- **完成 ≠ done**：成员跑完 → 任务转 `in_review`（待验收）；`done` 只能由人确认。
- 部分完成：完成项 `in_review`、失败项 `blocked`；**下游不解锁**。
- 全队失败 → 团队整体 `failed` + 可重试。

## 六、治理红线（固定，不可配）

1. **执行侧不得写 `done`**：任何来自团队/成员/尝试的写请求，若目标状态 = `done` → 拒绝 + 审计。
2. **未授权不开工**：`backlog` 任务不得被团队认领。
3. **审查未过不解锁下游**：`kind=review` 未 pass → 下游保持 `blocked`。

执行侧可写：`in_progress` / `in_review` / `blocked` / `canceled`。
**"两个 done 不相等"**：本项目库的 `done`（人工确认）≠ 承载环境 agent team 的 `completed`（成员跑完）；红线只作用于"执行侧回流到本项目库的写路径"。

---

## 七、边界与严禁

- 不 commit / 不 push / 不 publish（commit 归队长/人；push/publish 需用户显式授权）。
- 不改范围外文件；同一文件串行修改（不并行改同一文件）。
- 不隐藏失败：失败原样上报，禁止"重试到成功再报"。
- 不进入交互式会话；不在无授权目录落盘。
- 不绕开工作台 API 直接改库。

### 8.1 分域声明（2026-10-23 · 只增不改）

**本文件约束的是「工作台派发路径」**：经工作台/承载环境（DSH）创建的团队，怎样建、怎样派、怎样回写、红线是什么。**编制单位＝角色（executor）**。

**被派发项目自有的「会话团队」设定不在本文件作用范围内。** 典型例子：`项目-dsh-acp/docs/项目团队.md` 的 A/B/C 会话拓扑（Planner 独立 · Executor/Coder 共用同一会话 · Verifier 独立）。本文件**不改写、不降级、不覆盖**它们 —— 它们约束的是「人 ⇄ 会话」手转时的协作方式，**编制单位＝会话**。

**路由规则（何时走哪条）**：

| 触发场景 | 走哪条路径 | 权威文档 |
| --- | --- | --- |
| 经工作台/DSH 把任务派发给 agent team（队友领取、证据回流看板、评审门把关） | 工作台派发路径 | **本文件** |
| 人直接开 A/B/C 类会话、人工转发指令（不经看板派发、不经评审门） | 项目自有会话团队 | **该项目自己的团队文档** |

**同名不同义（勿混用）**：工作台的 `planner` / `engineer` / `tester` / `reviewer` 是**派发单元（角色）**；项目的 `Planner` / `Executor` / `Coder` / `Verifier` 是**会话身份**。二者**语义可叠加**：同一件事可以是「会话 A 里的 Planner 同时作为工作台 `planner` 角色被派发」。读到时先问两件事 —— **这份文档是谁的**、**这个名字指的是角色还是会话**。

**若项目希望在工作台团队页看到自己的会话分工**：请在**项目侧**文档里写一份「角色 → 会话」映射（例如 `planner→A`、`engineer→B(Coder)`、`tester/reviewer→C`），**不要**为此改写本文件的角色定义。工作台团队页展示的是**派发角色**，不承担会话拓扑的表达。

**跨仓库不做的事**：本文件随包交付（见 `package.json#files`），被派发项目**无需自带**；**不在被派发项目里新建第二份 `团队agent.md`**（另建即制造重复与漂移）。

**分域后仍不变的红线**：无论走哪条路 —— `done` 只能由人确认（执行侧可写 `in_progress` / `in_review` / `blocked` / `canceled`）；`backlog` 不得开工；审查未过不解锁下游。

## 九、智能体操作规范（随包）

> **本条与 FR-07 同源，不得另立第二份规范**：本节是 FR-22 所要求的「智能体操作规范」正本清单，随包交付（见 `package.json#files`），并与 [`需求文档.md`](./需求文档.md) 的 FR-07 边界一致（**先读 → 认领 → 执行 → 提交待验收 → 人确认**）。本节可独立阅读，不与本文件其它条款矛盾；若与 FR-07 出现表述分歧，**以 FR-07 为准**。

**一份自洽清单（六条，按操作顺序）**：

1. **先读任务与评论再动手**。接单前先读该任务的状态、描述、**全部评论**与 `acceptance`（验收口径／复核动作）；未读过就动手视为违规。读到的信息与预期不符（例如目标未归因），先停手确认，不要"边猜边干"。
2. **`backlog` 不得执行**。处于 `backlog` 的任务，智能体**不得认领、不得推进**；只有人把它移出 `backlog`（到 `todo` 等可开工状态）后才可认领。被拦截是**预期**，不是"缺 todo"（互链：§三 派发协议、§六 红线 2）。
3. **认领需声明身份**。认领（进入进行中）＝"由我负责"，必须**显式声明身份**：角色 + 实例（如 `engineer@<实例>`）以及所在会话；系统会记录认领者/会话身份。匿名认领视为无效。
4. **完成后提交待验收并附证据**。跑完只能把任务提交为 `in_review`（**待验收**），并附上"做了什么、怎么验证的"证据：diff 摘要 / 退出码 / 测试结果（`node --check` + `node --test`）/ 复现步骤。部分完成：完成项 `in_review`、失败项 `blocked`，下游不解锁（互链：§五 反馈回写契约）。
5. **`done` 必须由人确认**。智能体**没有任何手段**把任务置为 `done`；`done` 只能由人在界面或命令行显式确认。执行侧可写状态仅 `in_progress` / `in_review` / `blocked` / `canceled`（互链：§六 红线 1、§五"完成 ≠ done"）。
6. **与他人冲突需重读再改**。发现目标已被他人改动（他人认领、评论新增、状态变化）时，**重读**最新版本再改，不得凭旧快照覆写；版本冲突按 `VERSION_CONFLICT`（退出码 5）处理 —— 重新读取 → 以最新版本重做改动 → 再提交，**不要**盲目重试同一份旧载荷。

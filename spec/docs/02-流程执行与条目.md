# 02 · 流程执行与条目写法

> 这一份管两件事：**活怎么走**（全环 + 指令 + 证据）与**条怎么写**（骨架 + 预算 + 反模式）。

---

## 一、全环（缺任一环，这轮就不算完成）

```
需求条目 → 任务卡（带 requirement_ref） → 认领（in_progress + owner）
        → 执行 → 证据评论（四节） → done → 需求关闭（先回读 ready）
```

四条硬规矩：

1. **卡必须挂需求**。没有 `requirement_ref` 的卡不允许开工；若确实不属于任何需求，先补建条目再开卡。
2. **认领先于动手**。`in_progress` + owner 是先写库、再干活；反过来做，看板上就永远看不出谁在干。
3. **证据评论不是汇报**。它是**下次复跑的说明书**：判定 / 偏离说明 / 边界自查 / 产物路径。
4. **关闭需求前先回读**。`completion` 里 `ready=false` 就说明还有卡没收口 —— 这时候关，等于把未完成记成完成。

> 计划外/新增需求同样走这条环：先建条目拿 ref → 建关联卡 → 可做则认领、不可做留 backlog。**不许停在口头。**

---

## 二、指令骨架（下发给执行 agent 时）

```
<编号>｜<一句话标题>

范围：<文件:行 / 条目编号 / 章节>；包含：…；移出：…
禁止：<项目硬禁令> + 本轮特禁
做法：分步；涉及改代码时写「先贴原文 → 改 → 再贴原文」
报告：证据四节 + 本类额外要什么读数
停下：<什么情况必须停、不停会怎样>
验收：<可复跑读数，一条一行，能判真假>
```

两条容易漏的：

- **「范围」必须同时写「包含」和「移出」**。只写包含 = 边界没定，执行侧会顺手扩。
- **「停下」不是客套**。写清「什么情况下停」，比写十遍「不要越界」有用。

---

## 三、条目骨架

### 任务卡（可执行单元 · 七块全填）

```
<编号>｜<动词开头：做完什么>

目标：这张卡做完，解决谁的什么问题（不写做法）
范围：<位置>；包含：…；移出：…
禁止：<相关硬禁令> + 本轮特禁
做法：分步
报告：四节证据 + 额外读数
停下：<停的条件>
验收：<可复跑读数>
关联：<需求 ref / 依赖卡 / 规范 §>
```

### 需求条目（可评估单元 · 五块必填）

```
<编号>｜<一句话标题>

目标：要解决什么（一句话）
范围：包含：…；移出：…
约束：口径、边界、红线
验收：3–6 条，可判真假
关联：条目 / 卡 / 文档 §
```

需求条目**可以省**「做法 / 报告 / 停下」—— 它说的是**要什么**，不是**怎么做**。

### 长度预算

| 对象 | 上限 | 超了怎么办 |
|---|---:|---|
| 需求条目描述 | 1200 字符 | 细节挪进卡或文档，正文只留指针 |
| 任务卡描述 | 800 字符 | 同上 |
| `acceptance` | 3–6 条 | 超过 6 条说明这件事该拆成两张卡 |

**禁止整段粘源文档**：写「见 `<路径>` §x」。整段粘贴就是 2000 字符截断的直接来源。

---

## 四、证据四节（每条都要能独立复跑）

```
① 判定      —— 逐条对验收给读数（命令 + 输出摘要），PASS/FAIL 明确
② 偏离说明  —— 计划外做了什么、为什么；没做的说明
③ 边界自查  —— 没碰什么（进程 / 数据 / 历史文档 / 未授权对外动作）
④ 产物路径  —— 改了哪些文件、文档落在哪、归档在哪
```

判据：**换个人只看这条评论，能不能不问你一句就把这轮复跑出来**。不能，就是没写完。

---

## 五、反模式（都真实出现过）

| 反模式 | 为什么坏 |
|---|---|
| `acceptance` 留空，验收写在正文 | 服务端只认字段；正文写了等于没写 |
| 正文一遍验收、字段再一遍且措辞不同 | 两个源必然走样；同一件事只准一个源 |
| 描述正好 2000 字符、结尾断在半个词上 | 早期导入的截断残片；界面标「残片」就别当完整依据 |
| 「验证通过」但不给读数 | 无法证伪，也无法复跑 |
| 用「上一轮说过要做」代替本轮批准 | 授权有有效期；破坏性动作必须当轮明确批准 |
| 只报「已完成」不报「没做什么」 | 边界是结论的一部分，缺失会被下次误读成「已覆盖」 |

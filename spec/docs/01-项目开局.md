# 01 · 项目开局（六步 + 自检表）

> 目的：把「打开工作台之后先干什么」这件事定死，避免项目一建就堆卡、卡一开就没人认得边界。

## 六步

### 1. 绑定工作区

项目必须有 **workspacePath**（你的代码仓库目录）。它是三件事的锚点：

- 项目副本写在哪：`<工作区>/.taskboard/`（文档、机器规范）；
- 执行单元的工作目录（`cwd`）；
- 开局自检、契约、证据里所有「相对路径」的基准。

> 没填工作区 ⇒ 副本生成会直接拒绝（`WORKSPACE_MISSING`），这不是 bug，是防止「静默写到不知道哪里」。

### 2. 建需求文档 + 第一条需求条目

需求条目是**可评估单元**，一张卡是**可执行单元**。先有需求，再拆卡 —— 反过来做，卡会没有归属，
后面既统计不了完成度，也没法回答「这件事为什么要做」。

条目骨架见 [`02-流程执行与条目.md`](./02-流程执行与条目.md) §三，模板见 [`assets/条目详情模板.md`](./assets/条目详情模板.md)。

### 3. 拆首卡：一张，带可判真假的验收

开局第一张卡不要贪大。判据：**做完之后，能用一条命令或一次点击判定真假**。

反例：「完善初始化流程」（不可判）→ 正例：「`POST /api/projects` 建项目后 `GET /api/projects/:id` 回读 `workspacePath` 一致」（可判）。

### 4. 确认执行能力（**必须标宿主版本 + pid**）

工作台能不能派发，取决于宿主能力位（会话创建 / 会话存在 / 归属查询…）。这些是**外部环境事实**，
不是本仓库常量 —— 所以任何「能力可用/不可用」的结论都要写清当时的 **宿主版本 + 进程号**，
否则升级之后旧读数会变成假事实（本项目实测过：宿主小版本升级就把三个能力位从 `false` 全翻成 `true`）。

### 5. 跑通第一条闭环

认领（`in_progress` + owner）→ 执行 → 证据四节 → `done`。第一张卡走完，才说明「看板不是摆设」。

### 6. 定验收口径再放量

放量之前确认三件事：验收写在哪（字段还是正文）、`done` 谁点、审查过不过谁来判。
这三条不定，卡越多越乱。

## 自检表（逐条能回答「是」才算开局完成）

| # | 检查 | 判据 |
|---|---|---|
| 1 | 工作区已绑定 | `GET /api/projects/:id` 的 `workspacePath` 非空 |
| 2 | 有需求条目 | 需求视图里至少 1 条 `open` |
| 3 | 首卡有验收 | 卡的 `acceptance` 非空且每条可判真假 |
| 4 | 卡归因到需求 | 卡上 `requirement_ref` 指向第 2 步的条目 |
| 5 | 执行能力已核实 | 能力读数带 **宿主版本 + pid** |
| 6 | 首条闭环走完 | 该卡 `done` 且证据四节齐全 |

## 反模式（开局阶段最常见的四个）

| 反模式 | 后果 |
|---|---|
| 先堆 20 张卡，没有需求条目 | 完成度无从统计；卡与卡之间的边界靠记忆 |
| 验收写在描述正文、`acceptance` 留空 | 服务端只认字段 ⇒ 等于「没有验收」 |
| 把整份需求文档粘进条目 | 早期导入就是这么截断的：2000 字符处断在半个词上 |
| 把「宿主能力」当常量写进文档 | 宿主一升级，文档与事实分叉，且没人会回头改 |

# item-detail · 条目详情规范（机器版）

> 这是 `docs/规范/07-条目详情规范.md` 的**随包机器版**：只留「骨架 + 预算 + 判据」，不带本仓的实测读数与存量清单。
> `docs/` 不入 git、不进包；**本文件才是装机后真正生效的那份**，也是 `contract_version` 里被 digest 化的那份。

## 两轨骨架

### 任务卡（可执行单元 · 7 块全填）

```
<编号>｜<一句话标题：动词开头，说清"做完什么">

目标：这张卡做完，解决谁的什么问题（一句话，不写做法）
范围：<文件:行 / 条目编号 / 章节>；包含：…；移出：…
禁止：<硬禁令里与本卡相关的那几条> + 本轮特禁
做法：分步；涉及改代码时写「先贴原文 → 改 → 再贴原文」
报告：四节证据（判定 / 偏离说明 / 边界自查 / 产物路径）+ 本类额外读数
停下：<什么情况必须停、不停会怎样>
验收：<可复跑读数，一条一行，能判真假>
关联：<需求 ref / 依赖卡 / 上游 PR / 规范 §>
```

### 需求条目（可评估单元 · 5 块必填）

```
<编号>｜<一句话标题>

目标：要解决什么（一句话）
范围：包含：…；移出：…
约束：口径、边界、必须守的红线
验收：3–6 条，可判真假
关联：条目/卡/文档 §
```

> 需求条目可省「做法 / 报告 / 停下」——它是**要什么**，不是**怎么做**。

## 长度预算

| 对象 | 上限 | 超了怎么办 |
|---|---:|---|
| 需求条目 `description` | 1200 字符 | 把细节挪进条目级的卡或文档，正文只留指针 |
| 任务卡 `description` | 800 字符 | 同上 |
| `acceptance` | 3–6 条 | 超过 6 条说明这件事该拆成两张卡 |

**禁止整段粘源文档**：写 `见 <path> §x`，不要复制正文。整段粘贴是 2000 字符截断的直接来源。

## 反例（真出现过）

| 反例 | 为什么坏 |
|---|---|
| 一段散文讲背景、方案、验收混在一起 | 读者要从散文里抠「范围」和「验收」，抠出来还不一致 |
| `acceptance` 留空，验收写在正文里 | 服务端只认字段；空字段＝「没有验收」，正文写了不算 |
| 正文写一遍验收、`acceptance` 字段又写一遍且措辞不同 | 两个源，必然走样（同一件事只准一个源） |
| 描述正好 2000 字符、结尾断在半个词上 | 早期导入的截断残片；界面会标「残片」，别当完整描述引用 |

## 自检（写完逐条过）

1. 第一行是不是 `<编号>｜一句话`？没有编号就先分配再写。
2. 「范围」是否**同时**写了「包含」与「移出」？只写包含＝边界没定。
3. 「验收」的每一条，拿给别人能不能**判真假**？不能就是没写完。
4. 有没有整段粘文档？有就改成指针。
5. 字符数是否在预算内（需求 ≤1200 / 卡 ≤800）？

## 这条规范自己怎么改

默认副本随包分发；项目里可复制一份到 `<工作区>/.taskboard/norms/` 自行修改。
**改正文必须同时 bump `version`**，否则 digest 校验会判定「规范被偷偷改了」，写操作会被按过期契约拦下。

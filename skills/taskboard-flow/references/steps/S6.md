# S6 · 需求变更

## 目标
需求改了，先把**影响面**摆出来，再决定改不改。

## 命令（两步，必须按顺序）
```
# ① 预览：不落地，只给影响面 + change_id
requirement_change { project, requirement, patch: { acceptance: "…" }, reason: "客户改了口径" }

# ② 落地：拿第①步的 change_id
requirement_change { project, requirement, patch: <同一个 patch>, reason: <同一个 reason>,
                     change_id: "<第①步返回>", apply: true }
```

## 判据
- 第①步 `applied === false`、`needs_approval === true`，且 `affected_cards` 列出这条需求下**未终态**的卡；
- 第②步 `applied === true`，`before` / `after` 与补丁一致；
- `governance_audit` 里有一条 `requirement-change`，`reason` 是你写的那句。

## 失败处置
| 错误码 | 该怎么办 |
| --- | --- |
| `CHANGE_NEEDS_APPROVAL` | 直接 `apply:true` 没带 `change_id` ⇒ 先预览 |
| `CHANGE_ID_MISMATCH` | 预览之后条目被改过，或你把补丁换了 ⇒ **重新预览**，别硬猜 |
| `CHANGE_REASON_REQUIRED` | `reason` 必填：没有理由的变更事后无法复盘 |

## 别做的事
- 不要跳过影响面直接改：`affected_cards` 是你唯一能看见"谁白做了"的时刻。
- 不要指望 `done` 卡自动重开 —— 它们**不会**；需要复查就新建一张卡。
